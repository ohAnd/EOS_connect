User Guide

Get EOS Connect installed and running, let the wizard configure it, and know where to look when something misbehaves.

Install

Pick one. All three end at the same place: a web UI on port 8081 that walks you through setup.

Home Assistant add-on

The easiest route if you already run Home Assistant.

  1. Add the ohAnd/ha_addons repository to your add-on store.
  2. Install EOS Connect and start it.
  3. Open http://homeassistant.local:8081.

The add-on only sets the web port, time zone and log level. Everything else lives in EOS Connect's own database and is configured in its web UI.

Docker

Works on anything that runs containers.

git clone https://github.com/ohAnd/EOS_connect.git
cd EOS_connect
docker compose up -d

Keep the ./data:/app/data volume. Your settings and the PV yield history the forecast auto-scaler learns from both live in data/eos_connect.db. Without that mount the database sits on the container's writable layer and is destroyed every time the container is recreated — which is exactly what an update does. Your settings then appear to have reverted on their own. Compose files written before v0.3.34 do not have it.

From source

Python 3.13.

git clone https://github.com/ohAnd/EOS_connect.git
cd EOS_connect
pip install -r requirements.txt
python src/eos_connect.py

Bootstrap settings

Almost everything is configured in the web UI and stored in the database. Only these infrastructure keys are read from config.yaml at startup, because they are needed before the database is open:

# config.yaml — bootstrap settings only
eos_connect_web_port: 8081  # web server port
time_zone: Europe/Berlin    # system time zone
log_level: info             # debug, info, warning, error

Each has an environment-variable equivalent, which wins over the file: EOS_WEB_PORT, EOS_TIMEZONE, EOS_LOG_LEVEL and EOS_DATA_PATH.

Upgrading? On first start EOS Connect migrates an existing config.yaml into the database by itself. Afterwards you can cut the file back to the keys above.

First run

On first launch a setup wizard opens and asks, in order, for the things it cannot guess. It saves only the answers it actually asked for — everything else keeps its default until you change it.

  1. Optimizer — built-in local solver, or an external EOS or EVopt server. The built-in one is preselected and needs nothing.
  2. EVCC (optional) — for PV forecasts, inverter control or car-charging-aware behaviour. Skip if you do not run it.
  3. Data source — Home Assistant, OpenHAB, or built-in defaults.
  4. Inverter — for battery control. Leave it on default for display only.
  5. Battery — capacity and charge limits.
  6. Load — your consumption sensor. Skipped automatically if no data source is connected.
  7. Price — your electricity tariff provider.
  8. PV installations — your solar forecast. Preset to a built-in demo curve so the first run finishes without your roof geometry.

Restart EOS Connect when the wizard finishes, and the dashboard starts filling in.

The Default PV source is a fixed demo curve for an assumed 4 kW array — not a forecast for your roof. It exists so you can see the system working immediately. Swap it for a real provider under Settings › PV Source once you are up.

Why the wizard asks in that order

  • EVCC and Data Source come before Inverter because either one can act as the inverter controller. Leave the EVCC URL blank and that option is greyed out later.
  • Sensor fields only appear once Data Source names Home Assistant or OpenHAB. Left unset, load and battery fall back to built-in defaults and say so in the log — they are never quietly polling a name you did not choose.
  • Every sensor field has a Test button that reads the entity and shows its current value, so a typo surfaces before you restart.
  • PV installations only matter for location-based forecast providers (Akkudoktor, Open-Meteo, Forecast.Solar). Solcast, Victron, EVCC and Timeseries get their data elsewhere.
  • A few choices need a setting the wizard does not ask for, because it is not a getting-started field. The Review & Finish step lists anything still outstanding.

Living with it

The dashboard shows the current plan: forecast solar, forecast prices, what the battery is being told to do and why. Change any setting behind the gear icon.

  • Override the battery by hand when you know something the optimizer does not — a set duration, then it hands control back.
  • Settings apply live where they safely can; the ones that need a restart are marked with a restart badge.
  • Back up before you experiment — there is a whole-install export and restore in Settings.

Update notifications

Running the Docker image, EOS Connect checks the container registry for a newer release twice a day and shows a dismissible banner when it finds one. It never updates itself — pulling the new image stays your decision. Home Assistant add-on users get updates through Home Assistant instead, so the check is off.

What your stored energy actually cost

EOS Connect tracks what went into the battery and at what price, so a discharge decision compares against the real cost of that stored energy rather than a guess. It separates solar charging from grid charging, and detects your sensor's sign convention rather than assuming one.

Forecast auto-scaling

Solar forecasts are generic; your roof is not. Auto-scaling compares forecast against measured yield over a rolling window and applies a correction factor, so the plan stops being systematically optimistic about a shaded array. See the PV auto-scaling settings.

Troubleshooting

Crashes on startup under Proxmox

Symptom: segmentation fault immediately at startup.

Cause: the VM is using the kvm64 generic CPU type, which hides the AVX and SSE4.2 instructions that the prebuilt numpy and pandas wheels need.

Fix: stop the VM, set Hardware › Processor › CPU Type from kvm64 to host, restart. This is safe and recommended for any Proxmox VM running containerised workloads.

"No such file or directory" for the CBC solver

Symptom: the built-in optimizer fails with FileNotFoundError: [Errno 2] No such file or directory pointing at solverdir/cbc/linux/i64/cbc — a file that is plainly there.

Cause: on x86_64 the CBC binary shipped inside pulp is dynamically linked against glibc, and the Home Assistant OS add-on images are Alpine-based (musl) with no glibc loader. Linux reports the missing loader as a missing file. aarch64 is unaffected.

Fix: update to the latest add-on version, which installs a statically linked CBC of its own. EOS Connect now verifies the solver by running it at startup and logs which binary it chose.

This one is often confused with the Proxmox problem above. A segfault is a CPU issue; a FileNotFoundError naming cbc is this one.

Self-signed certificates

EOS Connect validates TLS certificates when talking to Home Assistant or OpenHAB. With a private CA you can turn that off in Settings › Data Source › SSL Ignore (expert, needs a restart). Only do this on a network path you control — custom root CAs are not supported yet.

Settings revert after an update

Almost always the missing ./data:/app/data volume — see the Docker section. Add the mount, then reconfigure once.

A sensor reads nothing

Use the Test button next to the field. It fetches the entity and shows the current value, which distinguishes a wrong entity name from a connection or token problem. The log also names any sensor that fell back to a built-in default.

Reading the log

Set log_level: debug (or EOS_LOG_LEVEL=debug) and watch the startup sequence: it reports the selected optimizer backend, the solver binary, every interface it constructed, and every configured sensor it could not read. The web UI exposes the same log, with alerts filtered separately.
