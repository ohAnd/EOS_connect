Troubleshooting

Sorted by what you see, not by what the code calls it.

Troubleshooting

Crashes on startup under Proxmox

Symptom: segmentation fault immediately at startup.

Cause: the VM is using the kvm64 generic CPU type, which hides the AVX and SSE4.2 instructions that the prebuilt numpy and pandas wheels need.

Fix: stop the VM, set Hardware › Processor › CPU Type from kvm64 to host, restart. This is safe and recommended for any Proxmox VM running containerised workloads.

"No such file or directory" for the CBC solver

Symptom: the built-in optimizer fails with FileNotFoundError: [Errno 2] No such file or directory pointing at solverdir/cbc/linux/i64/cbc — a file that is plainly there.

Cause: on x86_64 the CBC binary shipped inside pulp is dynamically linked against glibc, and the Home Assistant OS add-on images are Alpine-based (musl) with no glibc loader. Linux reports the missing loader as a missing file. aarch64 is unaffected.

Fix: update to the latest add-on version, which installs a statically linked CBC of its own. EOS Connect now verifies the solver by running it at startup and logs which binary it chose.

This one is often confused with the Proxmox problem above. A segfault is a CPU issue; a FileNotFoundError naming cbc is this one.

Nothing starts after an EOS server update

Symptom: with eos.source set to eos_server, EOS Connect stops while starting up and the web interface never appears — so the settings cannot be reached either. The log ends with:

ERROR [Factory] Failed to create optimization_interface (critical=True):
  Failed to load optimizer configuration: 0
...
KeyError: 0

Cause: EOS reorganised how it stores devices. Its devices/electric_vehicles configuration used to be a list and is now keyed by device ID, and EOS Connect read the first entry by position while checking the server's charge rates.

Fix: update EOS Connect. It reads both layouts now, and leaves the charge rates alone on servers that fill them in themselves. A server configuration that does not look the way EOS Connect expects is logged from now on instead of stopping the start, so the settings stay reachable.

The EOS optimization horizon is not set

Symptom: with eos.source set to eos_server, the horizon on the EOS server stays at its default of 24 hours however often EOS Connect starts. Nothing in the log looks wrong — it even reports the horizon being set:

WARNING [OPT-EOS] Detected EOS version >= 0.1.0 - config updated with : {... 'horizon_hours': 48}

Cause: EOS moved the optimization horizon. It used to sit at optimization.horizon_hours; newer builds keep it per algorithm under optimization.genetic and optimization.genetic0 and no longer read the old key. EOS Connect wrote only the old one. Newer EOS does fold a flat value into the algorithm's section, but only where the nested value is still unset — and it never is, so the 48 was dropped without an error.

Fix: update EOS Connect. It now writes the horizon to the key the server actually reads for the request it receives, and reports a configuration update only when the server accepted it. Older EOS servers keep the previous behaviour. To check your server yourself:

curl http://<eos>:8503/v1/config/optimization/genetic0/horizon_hours

It should answer 48. On an EOS build that predates the split into genetic and genetic0 that path does not exist; /v1/config/optimization shows horizon_hours at the top level there instead.

What this horizon does, and does not do. Measured against EOS 0.2.0, 0.3.0 and a current dev build with a fixed optimizer seed: with the request EOS Connect sends — which carries all 48 slots of prices, PV and load — the horizon changes how far ahead EV charging is optimized, and nothing else. Battery charge, discharge and grid decisions came back identical at 24 and at 48, because the length of the supplied series already decides how far the plan reaches. So setting it right is worth doing if you charge an EV through EOS; it is not the difference between a one-day and a two-day battery plan.

Self-signed certificates

EOS Connect validates TLS certificates when talking to Home Assistant or OpenHAB. With a private CA you can turn that off in Settings › Data Source › SSL Ignore (expert, needs a restart). Only do this on a network path you control — custom root CAs are not supported yet.

Settings revert after an update

Almost always the missing ./data:/app/data volume — see the Docker section. Add the mount, then reconfigure once.

A sensor reads nothing

Use the Test button next to the field. It fetches the entity and shows the current value, which distinguishes a wrong entity name from a connection or token problem. The log also names any sensor that fell back to a built-in default.

The battery stops updating after a sensor drops out

Symptom: SOC, battery temperature and the dynamic charge power all freeze at their last values and never move again, while the rest of EOS Connect keeps running. A restart fixes it until the next time.

Cause: an entity that goes unavailable reports an empty state. Reading it crashed the background thread that refreshes the battery, and nothing restarts that thread.

Fix: update EOS Connect. An unreadable reading is now treated like any other failed fetch — the last known value is kept and the log says which sensor it was:

[BATTERY-IF] HOMEASSISTANT - Error fetching battery SOC:
  sensor returned an empty state. Failure count: 1/5. Using last known SOC = 42%.

After five failures in a row the SOC falls back to 5 % so the optimizer works from a safe assumption rather than a stale one. If the message repeats, the entity itself is the problem — check it in Home Assistant or OpenHAB.

Home Assistant history times out on startup

On a large recorder database — MariaDB with years of history is the usual case — building the load profile could flood Home Assistant with requests until they timed out:

[LOAD-IF] Request failed after 5 attempts for
  http://homeassistant:8123/api/history/period/2026-09-12T00:00:00
[LOAD-IF] DATA ERROR household load smaller than controllables
[BATTERY-IF] HOMEASSISTANT - Error fetching battery SOC: Request timed out.

The load profile is built from four fixed days of history — the same weekday one and two weeks back, plus the following day — so it only changes at midnight. It is now built once per day and held, instead of being rebuilt on every optimizer run, and each sensor's history is fetched once for the whole day instead of once per hourly slot. In the log you should see [LOAD-IF] creating load profile for weekdays … once a day, not every few minutes.

Nothing to configure. If you still see the messages above, the recorder itself is the bottleneck — check its purge settings.

Older days come back empty

Home Assistant's recorder purges detailed state history after purge_keep_days (10 by default), while the load profile looks back 14 days. For days whose history is gone, EOS Connect falls back to recorder statistics — five-minute buckets first, hourly long-term statistics second. Only the hourly ones are kept indefinitely; the five-minute buckets are purged on the same schedule as the history itself. At the default setting, the fourteen-day-old day therefore arrives as 24 hourly values.

Whether that matters depends on how finely you plan. At eos.time_frame 3600 it is the same profile either way — 24 values for 24 slots. At 900 it is not, because each hourly value then has to stand for four quarter-hours, and the shape within the hour is gone from half the samples the profile averages. If you plan in quarter-hours, set purge_keep_days: 15 under recorder in configuration.yaml and restart Home Assistant. It costs database size, in proportion to how many entities the recorder keeps.

That fallback calls the recorder.get_statistics action, so the long-lived access token needs permission to call services. On a Home Assistant too old to offer it, the log says so once and the profile simply uses the days it can still read.

A forecast provider is slow to answer

Symptom: the PV or outside-temperature forecast stops updating while the provider is having a bad day, and the log reports a timeout:

[PV-IF] Forecast.Solar did not answer within 5/12/30 s - the service is
  slow or unreachable; using the cached forecast

Cause: the public forecast services — Forecast.Solar, Open-Meteo and akkudoktor.net — normally answer in well under a second, but go through spells of double-digit response times. EOS Connect used to give each attempt the same five seconds, so retrying could not help: all three attempts hit the same wall.

Fix: update EOS Connect. Each attempt now waits longer than the one before — the PV forecast tries five seconds, then twelve, then thirty — so a slow spell is simply ridden out. Nothing to configure, and no extra requests are made: the number of attempts is unchanged.

The outside-temperature forecast does the same with two attempts, five seconds and then thirty. It settles for fewer deliberately: a held temperature curve is a perfectly good answer, where a held PV array is not, and every retry holds up the shared update cycle.

If the message appears anyway, the provider did not answer within thirty seconds. The last successful forecast keeps being used in the meantime, so a passing outage costs nothing. Note that Forecast.Solar's free tier allows 12 requests per hour per IP address — a separate limit, with its own message — see Who supplies the forecast.

Forecast.Solar rejects the API key

Symptom: the PV forecast never updates and the log repeats, once per cycle:

[PV-IF] Forecast.Solar rejected the API key (HTTP 401) - check api_key in
  Settings › PV Source, or clear it to use the public tier

Fix: correct the key under Settings › PV Source, or clear the field entirely — an empty key is valid and selects the free tier. A key that has expired or belongs to a different account gives the same message.

The key itself is never written to the log, and neither are your coordinates: both sit in the request path, so the URL is masked before it is logged. Log excerpts from this message are safe to paste into a bug report.

The optimization pauses for a whole quarter hour

Symptom: in quarter-hourly mode the optimization usually runs several times per slot, but now and then the log shows a pause of a full quarter hour right after a run:

[OPTIMIZATION] Quarter-hour aligned run: start 12:59:58, finish at 13:00:00
[Main] Next optimization at 12:59:58 (based on average runtime of 1 seconds). Sleeping for 15 min 0 seconds

Cause: a run that finished a few seconds before a quarter-hour boundary skipped that boundary, and the runs in between were not scheduled against the next one.

Fix: update EOS Connect. After such a run the next one follows at the usual interval.

Reading the log

Set log_level: debug (or EOS_LOG_LEVEL=debug) and watch the startup sequence: it reports the selected optimizer backend, the solver binary, every interface it constructed, and every configured sensor it could not read. The web UI exposes the same log, with alerts filtered separately.

Still stuck

Turn the log level up first — the startup sequence names the optimizer backend, the solver binary, every interface it built and every configured sensor it could not read, which is usually the answer on its own.
